## What changed in `re_rectifier.py` this session

1. **Value-shift detection** (`_looks_value_shifted` / `_cell_has_crammed_values`) — `_needs_fixing()` previously only checked for empty/`Column_N`/duplicate keys. A table with clean headers but silently row-shifted values (a common failure on twin-parallel-column layouts, e.g. a `%` column next to an `Absolute Count` column sharing one row grid) sailed through untouched. Now flagged via a domain-general signal: a cell holding two distinct value-like tokens crammed together.
2. **New fix-prompt rule (RULE 6)** — a worked example teaching the model to realign a shifted parallel column using the raw markdown's row order as ground truth.
3. **Row-count verification after the fix** (`_count_markdown_data_rows`) — found live, mid-session: the first fix attempt on the CBC table (26 rows) got silently truncated to 11 rows by a flat `max_tokens=600` cap. Nothing about the truncated output looked wrong syntactically, so the original value-shift check alone would have shipped it as "fixed." This check compares the fixed row count against the source table's row count and flags a mismatch.
4. **Dynamic token budget** (`llm_client.budget(..., ratio=0.8, floor=900, ceil=3000)`) — replaced the flat 600-token cap. This task's output tends to be *larger* than its input (rows gain keys, JSON syntax overhead exceeds markdown pipes), so the usual extraction-style ratio (>1) was inverted.

## Separately fixed this session: `run_tail.py` crash on single-document corpora

`delta_analyzer.run_delta_analysis()` returned early on zero cross-version topics *without writing* `delta_jobs_cache.json`. `run_tail.py`'s `step_delta_analyzer()` treats a missing cache file as a hard failure (`sys.exit(1)`) — so any single-document corpus (like this Sterling PDF, ingested alone) crashed the whole pipeline tail at step 4/12, before evolution analysis, indexing, or ChromaDB population ever ran. This is exactly what happened in your own `run_tail.log` this session, in a separate terminal, while this report was being generated. Fixed by writing an empty cache instead of skipping the write — confirmed live that `evolution_analyzer.py` and `topic_summarizer.py` already handle an empty/missing cache gracefully, so this was the one real gap.
